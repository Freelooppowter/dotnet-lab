## 二、本周踩的坑

### 坑 1：`dotnet-install.ps1` 跑起来像卡死

- **现象**：命令执行后光标闪烁，一行输出都没有，持续好几分钟。
- **我一开始以为**：脚本挂了 / 网络断了 / 命令写错了。
- **真正原因**：这个脚本默认几乎不输出进度，下载 200MB 期间就是静默的。而且它是**先下到 `%TEMP%` 再解压**，所以盯安装目标目录看大小变化完全没用。
- **正确的观察方式**：看 `%TEMP%` 下的 zip 是否在长大，或看 `powershell.exe` 的网络占用。排查可用 `-DryRun`（只解析不下载，会打印真实版本号和下载 URL）。

### 坑 2：用户级 PATH 被改坏了类型

- **现象**：改完 PATH 后，一批依赖 `%USERPROFILE%`、`%JAVA_HOME%` 的工具突然失灵。
- **我一开始以为**：路径写错了。
- **真正原因**：`[Environment]::SetEnvironmentVariable(..., 'User')` 会把 `REG_EXPAND_SZ` **降级写成** `REG_SZ`，PATH 里的 `%VAR%` 从"会展开"变成"字面字符串"。
- **正确做法**：直接操作注册表并显式保持类型：

  ```powershell
  $k = [Microsoft.Win32.Registry]::CurrentUser.OpenSubKey('Environment', $true)
  $kind = $k.GetValueKind('Path')
  $k.SetValue('Path', $newValue, $kind)
  ```

### 坑 3：用户级 PATH 永远打不过系统级 PATH

- **现象**：明明在用户 PATH 里加了新装的 SDK，`dotnet --version` 还是旧版本。
- **我一开始以为**：PATH 没刷新 / 装错了。
- **真正原因**：Windows 拼接进程 PATH 的规则固定为 `系统 PATH + 用户 PATH`，**系统永远在前，不可配置**。同名程序系统目录必胜。
- **后果**：`dotnet new -f net10.0` 报 `NETSDK1045: 当前 .NET SDK 不支持将 .NET 10.0 设置为目标`。这个报错看着像语法问题，实际是 SDK 选错。
- **解决**：在系统 PATH 最前面插入新路径，使其排在 `C:\Program Files\dotnet\` 之前。
- **不重启也能验证的技巧**：在当前会话里重新构造 PATH 再调用，可以立刻区分"配置错了"和"环境没刷新"：

  ```powershell
  $env:PATH = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')
  (Get-Command dotnet -All).Source
  dotnet --list-sdks
  ```

### 坑 4：`chmod 600` 在 Windows 上不管用

- **现象**：Git Bash 里 `chmod 600` 显示成功，但 Windows 自带的 ssh 拒绝加载私钥，报 `UNPROTECTED PRIVATE KEY FILE`。
- **我一开始以为**：权限已经收紧了。
- **真正原因**：**Git Bash 的权限位不映射到 NTFS ACL**。所以 Git 自带的 ssh（检查宽松）能用，Windows 自带的 ssh（检查严格）直接拒绝 —— 同一个配置在两个客户端上表现完全不同。
- **解决**：

  ```powershell
  icacls "E:\dev\secrets\id_ed25519_gh" /inheritance:r /grant:r "$($env:USERNAME):R"
  ```

### 坑 5：noreply 邮箱写错格式，提交能推但不关联账号

- **现象**：提交推上去了，但 GitHub 显示灰色默认头像，不计入贡献图。
- **我一开始以为**：`用户名@users.noreply.github.com` 就是正确格式。
- **真正原因**：GitHub 的 noreply 地址按注册时间分两种 —— 2017-07-18 之后注册的是 `数字ID+用户名@...`，之前注册且当时开了隐私的才是 `用户名@...`。**写错不会报错，只会悄悄丢关联。**
- **验证方式**：查 commits API，看 `author` 字段是否为 `null`：

  ```bash
  curl -s https://api.github.com/repos/<用户名>/<仓库>/commits
  ```

- **最保险**：去 `https://github.com/settings/emails` 看页面显示的确切地址。

### 附：两个 cmd 层面的小陷阱

- **`cd` 跨盘静默失败**：`cd E:\dev\src\xxx` 在 C 盘时**不报错也不切换**，必须 `cd /d E:\...`。因为不报错，很容易在写了一半文件后才发现文件落在了错误的位置。
- **`--list` 不等于"删掉了另一层"**：`git config --list` 列出的是**合并后的全部层级**，`--local` 只是覆盖、不是删除。看生效值用 `git config user.name`（不带 `--list`）。

## 三、本周观察到的共性

上面五个坑有一个共同特征：**都不报错，只会在结果上悄悄偏掉。**

它们报出来的错还都指向别处 —— 把"SDK 选错"报成"框架不支持"，把"ACL 太宽"报成"权限错误"，把"邮箱格式不对"表现成"头像灰的"。

这一类问题比崩溃难查得多，因为第一反应总是往报错信息指向的方向找。记录时保留"我一开始以为"这一栏，就是为了留下这条误导路径。
