## 二、本周踩的坑

### 坑 1：`dotnet-install.ps1` 跑起来像卡死

- **现象**：命令执行后光标闪烁，一行输出都没有，持续好几分钟。
- **我一开始以为**：脚本挂了 / 网络断了 / 命令写错了。
- **真正原因**：这个脚本默认几乎不输出进度，下载 200MB 期间就是静默的。而且它是**先下到 `%TEMP%` 再解压**，所以盯安装目标目录看大小变化完全没用。
- **正确的观察方式**：看 `%TEMP%` 下的 zip 是否在长大，或看 `powershell.exe` 的网络占用。排查可用 `-DryRun`（只解析不下载，会打印真实版本号和下载 URL）。

### 坑 2：用户级 PATH 被改坏了类型

- **现象**：改完 PATH 后，一批依赖 `%USERPROFILE%`、`%JAVA_HOME%` 的工具突然失灵。
- **我一开始以为**：路径写错了。
- **真正原因**：`[Environment]::SetEnvironmentVariable(..., 'User')` 会把 `REG_EXPAND_SZ` **降级写成** `REG_SZ`，PATH 里的 `%VAR%` 从"会展开"变成"字面字符串"。
- **正确做法**：直接操作注册表并显式保持类型：

  ```powershell
  $k = [Microsoft.Win32.Registry]::CurrentUser.OpenSubKey('Environment', $true)
  $kind = $k.GetValueKind('Path')
  $k.SetValue('Path', $newValue, $kind)
  ```

### 坑 3：用户级 PATH 永远打不过系统级 PATH

- **现象**：明明在用户 PATH 里加了新装的 SDK，`dotnet --version` 还是旧版本。
- **我一开始以为**：PATH 没刷新 / 装错了。
- **真正原因**：Windows 拼接进程 PATH 的规则固定为 `系统 PATH + 用户 PATH`，**系统永远在前，不可配置**。同名程序系统目录必胜。
- **后果**：`dotnet new -f net10.0` 报 `NETSDK1045: 当前 .NET SDK 不支持将 .NET 10.0 设置为目标`。这个报错看着像语法问题，实际是 SDK 选错。
- **解决**：在系统 PATH 最前面插入新路径，使其排在 `C:\Program Files\dotnet\` 之前。
- **不重启也能验证的技巧**：在当前会话里重新构造 PATH 再调用，可以立刻区分"配置错了"和"环境没刷新"：

  ```powershell
  $env:PATH = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')
  (Get-Command dotnet -All).Source
  dotnet --list-sdks
  ```

### 坑 4：`chmod 600` 在 Windows 上不管用

- **现象**：Git Bash 里 `chmod 600` 显示成功，但 Windows 自带的 ssh 拒绝加载私钥，报 `UNPROTECTED PRIVATE KEY FILE`。
- **我一开始以为**：权限已经收紧了。
- **真正原因**：**Git Bash 的权限位不映射到 NTFS ACL**。所以 Git 自带的 ssh（检查宽松）能用，Windows 自带的 ssh（检查严格）直接拒绝 —— 同一个配置在两个客户端上表现完全不同。
- **解决**：

  ```powershell
  icacls "E:\dev\secrets\id_ed25519_gh" /inheritance:r /grant:r "$($env:USERNAME):R"
  ```

### 坑 5：noreply 邮箱写错格式，提交能推但不关联账号

- **现象**：提交推上去了，但 GitHub 显示灰色默认头像，不计入贡献图。
- **我一开始以为**：`用户名@users.noreply.github.com` 就是正确格式。
- **真正原因**：GitHub 的 noreply 地址按注册时间分两种 —— 2017-07-18 之后注册的是 `数字ID+用户名@...`，之前注册且当时开了隐私的才是 `用户名@...`。**写错不会报错，只会悄悄丢关联。**
- **验证方式**：查 commits API，看 `author` 字段是否为 `null`：

  ```bash
  curl -s https://api.github.com/repos/<用户名>/<仓库>/commits
  ```

- **最保险**：去 `https://github.com/settings/emails` 看页面显示的确切地址。

### 坑 6：配了国内镜像，反而把包恢复拖死了

- **现象**：`dotnet build` 卡了三分钟没有任何输出；`dotnet new xunit` 直接超时被中断。
- **我一开始以为**：网络太慢 / SDK 装坏了 / 项目模板有问题。
- **真正原因**：机器级 NuGet 配置里配的国内镜像地址**已经失效**（返回 HTTP 404）。NuGet 恢复时会遍历所有已配置的源，坏源会导致长时间等待，而且**不报错，只是慢**。
- **诊断方法**：直接对每个源发一次 HTTP 请求，看状态码和耗时，不要靠猜：

  ```bash
  curl -s -o /dev/null -m 15 -w "HTTP %{http_code}  %{time_total}s\n" <源地址>
  ```

  实测结果：官方源 `302 / 0.48s`（通）、国内镜像 `404`（已失效）、另一个国内镜像 `200 / 0.2s`（可用）。

- **解决**：在仓库里放一份 `NuGet.config`，用 `<clear />` 丢弃所有继承来的源，只留可用的。**放在仓库里而不是改全局**，避免影响同一台机器上的其他使用者。
- **效果对比**：修复前 3 分钟没跑完，修复后 `build` 5.15 秒完成。

- **教训**：不是为了"提速"而配镜像。镜像一旦失效，它会变成**负优化**——比不配还慢，而且静默。国内开发环境下，这个配置值得定期复查。

### 附：两个 cmd 层面的小陷阱

- **`cd` 跨盘静默失败**：`cd E:\dev\src\xxx` 在 C 盘时**不报错也不切换**，必须 `cd /d E:\...`。因为不报错，很容易在写了一半文件后才发现文件落在了错误的位置。
- **`--list` 不等于"删掉了另一层"**：`git config --list` 列出的是**合并后的全部层级**，`--local` 只是覆盖、不是删除。看生效值用 `git config user.name`（不带 `--list`）。

### 4.1 命令清单

以下命令在 `E:\dev\src\dotnet-lab` 下依次执行：

```powershell
# 1. 解决方案。注意 .NET 10 默认生成 .slnx（XML 格式），不是传统的 .sln
dotnet new sln -n DotnetLab

# 2. 类库与测试项目。-f 锁目标框架，-o 指定输出目录
dotnet new classlib -n DotnetLab.Core  -f net10.0 -o src\DotnetLab.Core
dotnet new xunit    -n DotnetLab.Tests -f net10.0 -o tests\DotnetLab.Tests

# 3. 把两个项目加入解决方案。.NET 10 会自动按 /src/ /tests/ 分 Folder
dotnet sln DotnetLab.slnx add src\DotnetLab.Core tests\DotnetLab.Tests

# 4. 测试项目引用被测项目
dotnet add tests\DotnetLab.Tests reference src\DotnetLab.Core

# 5. 两个模板文件
dotnet new gitignore
dotnet new editorconfig
```

### 4.2 哪些不是命令生成的

下面四个文件是手写的，`dotnet new` 没有对应模板（或模板产物不符合需求）：

| 文件 | 为什么手写 |
|---|---|
| `Directory.Build.props` | 统一编译配置，需要自定义 `WarningsAsErrors=nullable` 和 CI 分支 |
| `global.json` | `dotnet new globaljson` 会多写 `allowPrerelease` 等字段，这里只需要锁定版本 |
| `NuGet.config` | 需要 `<clear />` 丢弃继承来的坏源，模板不含此逻辑 |
| `README.md` | 纯手写 |

### 4.3 当时的一个中途失败

`dotnet new xunit` 第一次执行时**卡在 NuGet 包恢复阶段，最后超时中断**。原因不是模板有问题，而是全局配置里有失效的镜像源（坑 6）。补上 `NuGet.config` 之后，同样的命令几秒完成。

**顺序上的教训**：仓库里应该**先有 `NuGet.config`，再跑任何带包恢复的 `dotnet new`**。这次是先建项目、后修源，白白浪费了一次中断。

### 4.4 事后如何反推用过什么命令

没有历史记录时，可以从产物倒推，因为这些模板的产物特征很稳定：

| 想确认 | 怎么看 |
|---|---|
| 用了哪个模板 | 看 `.csproj` 的 `Sdk`、`TargetFramework`、`PackageReference` 组合。`xunit` 模板会带 `coverlet.collector` + `Microsoft.NET.Test.Sdk` + `xunit.runner.visualstudio` 三件套 |
| 项目名与目录 | `-n` 决定项目名，`-o` 决定落盘位置，两者可以不同 |
| 目标框架 | `.csproj` 里的 `<TargetFramework>` |
| 是否被加入解决方案 | `.slnx` / `.sln` 里是否有对应 `Project Path` |
| 引用关系 | `.csproj` 里是否有 `<ProjectReference>` |
| 有哪些可用模板 | `dotnet new list`，加 `--detail` 看模板参数 |

### 4.5 为什么终端历史里查不到

因为**执行方不是你的终端**。

这些命令跑在独立的 shell 进程里（Git Bash，通过工具逐条启动），而 PowerShell 的 `Get-History` / `ConsoleHost_history.txt` 只记录**你自己在那个窗口敲的**内容。两者互不相通：

| | 记录位置 | 谁产生 |
|---|---|---|
| 你的 PowerShell 历史 | `%APPDATA%\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt` | 你自己敲的命令 |
| 我的执行 | 独立进程，命令结束后不落盘 | 工具调用 |

顺带一个更容易被忽略的点：**每条命令都是新进程，连 shell 变量都不保留**。所以 `DT=/e/dev/dotnet/dotnet.exe` 这种变量赋值在同一行命令里有效，跨命令就失效——这也是当时每条命令都写完整路径的原因。

**结论**：凡是希望日后能复现的搭建动作，必须当场写进文档，不能指望终端历史。这条对人对 AI 都成立。
